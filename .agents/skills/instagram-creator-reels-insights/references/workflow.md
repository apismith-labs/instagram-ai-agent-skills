# Workflow contract

This reference is part of the Skill execution path. Read it before each report and run `python3 <skill-directory>/scripts/workflow.py` with one JSON object on stdin for `settings`, `window`, `select`, `split`, and `reconcile` as applicable. The helper is offline, makes no network calls, and stores no settings. If the host cannot safely execute it or supply private in-memory inputs, explain that host limitation and do not start Actor calls.

## Configuration and user interaction

A report uses the public account list, a positive integer `per_creator_limit`, and whether the user agreed to save the account list and limit. The first setup confirms these items only; do not request a report budget or per-run cost option. Routine requests reuse settings available in the current session or supported, user-authorized storage. Otherwise provide a reusable prompt. For backward compatibility, an older settings object may contain `report_budget_usd`; ignore it and never return or use it.

If Apify is disconnected, stop relevant calls and direct the user to the current host's connection settings. Never request secrets in chat. Be transparent that the report invokes discovery and transcript processing, possibly across multiple runs, and that actual usage follows the user's Apify account and each Actor's current billing rules. Do not estimate or promise fees, or repeatedly interrupt to ask about a budget. The user can inspect actual usage in Apify Console. Follow the host's own approval requirements.

For Daily/Weekly boundaries call `window` with request time and mode. Preserve `end_utc_exclusive` in every later `select` call. Pass the requested IANA timezone as `display_timezone` to `select`; if the request has no timezone, use and label `UTC`.

## Host tools and live contracts

Use only tools actually exposed by the selected host and their current live schemas. Do not assume one universal tool name, argument structure, or permission model. Before Profile Posts discovery, confirm the exact target Actor, authorization, live input schema, run-status query capability, and result/Dataset read capability. Do not require an output enum or verified media-type mapping before this discovery/read phase. Read and preserve actual returned rows before deciding which records can be classified. If a required access or input/read capability is missing, stop that Actor call and state the specific blocker. Verify the Transcript contract before any Transcript call. Do not block normal use because `callOptions`, `maxTotalChargeUsd`, `maxItems`, or run-options readback is absent; run-level budget planning and cost controls are outside this Skill's requirements.

## Retrieval and processing limits

`per_creator_limit` is a local transcript-processing cap applied after discovery. It is not an Actor input and must never be passed as `resultsLimit`. Every `apple_yang/instagram-post-scraper` discovery request must explicitly include the JSON field `"skipPinnedPosts": true`; do not rely on the Actor default. Confirm the live schema accepts this boolean before calling; if absent or conflicting, stop and report the mismatch rather than omitting or changing it. This input is for Profile Posts only and must not be passed to the Transcript Actor. The project has no user override for this default. A true value skips pinned posts, including posts in the requested time window. Disclose that coverage limitation and report an excluded-post count only if the Actor returns a verifiable count; never imply that all time-matching posts were covered. When the live Profile Posts schema supports the required field/value, use `resultsLimit=50` as the project default. This default comes from the project owner's prior runtime observation of a per-Creator result/usage limit; the public schema only describes a maximum result count and does not guarantee per-Creator semantics. Keep each discovery run to one requested username while scope behavior remains unverified. If the live schema no longer supports any required input, stop on that schema mismatch rather than omitting it or substituting `per_creator_limit`.

The raw returned row count reaching `resultsLimit` means results may have been capped or truncated. When a run is `SUCCEEDED`, its Dataset has been fully read with evidence, and the Creator's raw row count is below the configured limit, report in the user's language that the Actor-returned Dataset was fully read and the configured result limit was not reached. This refers only to the returned Dataset and does not guarantee that all posts in the requested time window were found. Do not infer Dataset completeness from run success, a row count below the limit, an empty result, or absence of a truncation marker. Missing pagination metadata or extra completeness flags do not block processing validated returned rows, but coverage must remain conservative and no full-window scan may be claimed.

### OpenClaw Apify Dataset collection compatibility

Keep three counts separate: `dataset_total` is the Dataset's total row count; `result_count` represents rows the plugin read into memory (the original plugin's `resultCount`); `returned_items` is the paginated collector's returned rows; `model_visible_rows` is the number of complete, parseable records actually present in `posts` for helper processing. Never use `resultCount` by itself as the model-visible row count or Dataset total.

For the original OpenClaw Apify plugin v0.5.3, the project audit found that `collect` serialized Dataset output with a 50,000-character cap and did not expose pagination or structured truncation metadata. On that version, `SUCCEEDED`, `allDone`, `resultCount`, one successful `collect`, or a `resultCount` below the Actor limit does not prove complete Dataset retrieval. An observed `[…truncated]`, `... N more characters truncated`, incomplete JSON, `truncated: true`, `hasMore: true`, or a source count greater than model-visible rows is explicit incomplete evidence: set `retrieval_complete=false` and retain the observed source/detail. `truncation_markers` is the list of non-empty marker strings actually observed; every non-empty valid list means incomplete, even if its marker text was not previously known. If no such signal exists but there is no reliable total or terminal-page evidence, use `null`/unknown; absence of a marker is not proof of no truncation.

For paginated tools, continue using each `nextOffset` until a reliable terminal signal. `next_offset` must be `null` or a non-negative integer; strings, objects, negative numbers, and Booleans are invalid. The current evidence contract recognizes normalized `next_offset_kind` values `exact` and `speculative` (trim surrounding whitespace and compare case-insensitively); unknown values cannot establish completeness. `nextOffsetKind="speculative"` only permits probing a possible next page; it does not prove that a page exists. `next_offset_kind` describes the cursor emitted by the page represented by the evidence; if the evidence says all pages were read, this must be the terminal page. Put any retained speculative cursor from an earlier page in a separate `prior_page_cursors` field, not in the terminal page field; the helper preserves but does not validate that historical field. A terminal page with `hasMore=false` conflicts if `next_offset` is non-null or `next_offset_kind` is `speculative`; a matching `dataset_total` cannot override that conflict. Set `retrieval_completeness_conflict=true` and never `retrieval_complete=true` for such evidence. `retrieval_complete=false` remains false when evidence is insufficient; when it conflicts with otherwise reliable complete evidence, retain false and mark the conflict. A complete read requires complete JSON and either an exact `dataset_total == model_visible_rows` match or traceable evidence that all pages were read and the terminal page reported `hasMore=false`, without truncation, cursor conflict, or count contradictions. Any non-empty valid `truncation_markers` list is explicit incomplete evidence. Normalize evidence into `retrieval_complete_evidence` with non-empty `source` and `detail`, plus applicable fields: `dataset_total`, `result_count`, `returned_items`, `model_visible_rows`, `truncated`, `truncation_marker_detected`, `truncation_markers`, `json_complete`, `has_more`, `all_pages_read`, `next_offset`, and `next_offset_kind`. The helper validates current-page cursor types/consistency and count consistency; it preserves but does not validate `prior_page_cursors`, and cannot authenticate the source or truth of host evidence. These normalized enum spellings are repository evidence-contract values, not confirmation of a live plugin enum.

A separately tested isolated plugin copy exposed pagination fields and read a Dataset 24/24 without second truncation in the tested model response. It was not the official installed v0.5.3 plugin. Do not generalize that result to the official plugin or direct ordinary users to install an unpublished isolated copy.

## Profile discovery and video selection

Use the requested half-open report interval (inclusive start, exclusive end) and filter returned records locally. The `select` helper accepts per-run bundles with a unique `run_id`, submitted `usernames`, `results_limit`, exact `run_status`, all raw `posts`, and optional `retrieval_complete` evidence. Preserve raw rows and source/run status. For discovery, `retrieval_complete` is tri-state: `true`, `false`, or `null` (unknown; omission is also unknown). The helper requires non-empty `source` and `detail` in the evidence object. It accepts `true` only when `json_complete=true` and either `dataset_total` equals the helper's actual `model_visible_rows`, or `all_pages_read=true` with terminal `has_more=false`, with no truncation, cursor conflict, or count conflict. Explicit truncation/more-pages/count-gap evidence makes it `false`; absent or insufficient proof remains `null`. An explicit input `false` remains false when the evidence has no complete-read proof; if reliable complete evidence contradicts it, the status stays false and `retrieval_completeness_conflict` is true. A claimed `true` that conflicts with explicit incomplete or inconsistent evidence is fail-closed and carries the conflict flag. Preserve `retrieval_complete_evidence` as provided; the helper does not create evidence or authenticate its source/truth. Never infer it from `SUCCEEDED` alone. This discovery field is distinct from the Transcript reconciliation field `dataset_complete`; do not copy one state into the other. If pagination/completeness is unknown, retain returned rows and classify them but do not claim a full scan.

Use the Profile Posts Actor's contracted post-publication field as the primary time source. The confirmed runtime observation for the current Profile Posts `timestamp` and Transcript Actor post `createTime` values is numeric Unix seconds. Supply `timestamp_unit: "unix_seconds"` in the helper's `post_contract` only when the current field/value contract confirms that unit; the helper never infers seconds versus milliseconds from magnitude or from a field name. Parse verified Unix seconds to one UTC instant, compare that instant against the helper's UTC window boundaries, and derive display time from that same instant using `display_timezone`. The selected record includes `published_at_utc`, `published_at_local` and `display_timezone`; display `published_at_local` with its timezone label and do not relabel the UTC value as local time. If a value's type, unit or timezone is unknown/unparseable, preserve it in the unresolved row as `timestamp_unverified`, including field name, presence and raw value, and do not guess its window membership or display date. The Transcript Actor's string `timestamp` is its run time, not a post publication time. Its `createTime` may only cross-check the primary discovery time after existing URL/ID reconciliation confirms that both rows represent the same post; it does not replace the primary timestamp.

The project owner confirmed the transcription rule: a record is eligible only when its `type` is exactly the case-sensitive string `"Video"` and it has a usable Instagram post `url`. The current public Actor output schema declares `type` as a string with no enum; the exact `"Video"` handling is project policy, not an Actor schema guarantee. `productType` is not a gate. Do not distinguish Reel from regular video post, and do not use `isReel`, `productType`, URL shape, field names, or guessed mappings to infer eligibility. Missing, null, non-string, or any other `type` value is unknown: preserve the row and actual type field presence/value, but never send it to the Transcript Actor. No missing Reel enum, pagination metadata, or extra completeness flag is a reason to block a returned exact-Video record from processing.

Per-Creator counters have distinct meanings:

- `returned_raw_rows`: all Dataset rows read for a run mapped to exactly one Creator, before local filtering. Use `null` when rows from a multi-Creator or unmapped run cannot be apportioned.
- `discovered_returned_in_window`: attributable raw rows with valid Creator identity, usable post URL, and timestamp in the requested interval, regardless of media type. This counts duplicate raw rows.
- `type_video_candidates`: deduplicated in-window rows whose `type` is exactly `"Video"` and whose URL is usable, before `per_creator_limit`.
- `unknown_media_type`: count of attributable in-window raw rows whose type is missing, null, non-string, or not exactly `"Video"`; includes duplicates and does not require a usable URL. It is an unknown-type row count, not an interface-error count.
- `selected` and actually processed: candidates selected under `per_creator_limit`, and the subset with transcript processing attempted/completed. Report the relevant run status separately.

`discovered_returned_in_window` is not an all-posts-found count. Count attributable in-window raw rows with usable URLs regardless of media type, preserving duplicates. Deduplicate exact-Video candidates before applying the local processing cap. Unknown rows remain auditable as `unknown_media_type` with the type field name, `field_present`, and actual `value`; they are not zero confirmed videos. Missing, null, non-string, or other non-`"Video"` type values do not increment `row_interface_error_count` and do not by themselves produce `partial_interface_error`; they do keep coverage partial and must be disclosed. A confirmed `"Video"` row with no usable URL is a structural interface error. Mixed results may proceed with exact-Video rows while unknown rows are disclosed. If every in-window row has an unknown type, report that posts were returned but the type rule did not confirm which are videos; do not say there were no videos. If no exact-Video candidate is selected, call neither the Transcript Actor nor `reconcile`.

Required structural fields and reliable run-to-Creator mapping remain necessary to classify/process rows. Preserve malformed, conflicting, or unattributable data as unresolved with its actual evidence. A missing run mapping may use only the existing independently verifiable requested-Creator row fallback; keep coverage unknown. A missing discovery run means no rows were returned for that Creator in this attempt, while coverage and additional candidates remain unknown. Valid attributable exact-Video rows from failed or incomplete runs may still be transcribed; retain the run status and mark coverage partial/unknown. Never claim complete time-window coverage based only on returned rows or a below-limit count.

## Transcript batches and reconciliation

Re-read live Transcript Actor schema and account limits. Build batches only from selected, deduplicated URLs and within a batch size supported by the live Actor schema/account. Split batches internally when supported; do not hide calls, automatically retry, or expand scope. Reconcile against the full submitted list so each post gets a result even when the Actor returned no row. Use exact/canonical URL first, then only the verified post ID kind (code or pk); never use result order. Distinguish explicit empty text, missing text, invalid structure, segment-only results and Actor error, no returned row, duplicate rows, identity conflict, unmatched URL and Dataset incompleteness. Preserve valid segments when top-level text is absent, but do not concatenate them unless the live contract proves a safe delimiter. Never interpret missing text as no speech. Do not retry automatically.

A complete transcript Dataset count requires terminal run state plus complete Dataset/page evidence from the host. If unavailable, mark results provisional and report the limitation. `dataset_complete` may be `true`, `false`, or `null`; if the CLI field is omitted, it is treated as `null` (unknown), not as explicit false and not as complete. A `reconcile` row status of `success` means only that the returned transcript row was reliably matched to its submitted post; it says nothing about discovery completeness or whether the transcript Dataset itself was fully read. Every submitted-post result preserves the `dataset_complete` value, including duplicate-row and identity-conflict results. Before reconciliation, pass both verified contracts: `post_contract` and `transcript_contract`. `post_contract` must require the project processing value `video_values: ["Video"]` and no other value mapping. Call `reconcile` only when at least one exact-Video candidate was submitted to the Transcript Actor and that run result set/status is available; do not call it for an all-unknown or otherwise empty selection. The helper rejects an empty submitted-candidate list. Unknown media rows are never submitted. Their stable ID kinds must match unless a specific reliable mapping has been separately verified; this implementation has no such mapping, so a mismatch or missing contract is an interface error before row matching.

For `reconcile`, `run_error` is an optional input containing only the error text or status message actually returned by the host for that same run. Never invent an error or map a message from another run. Only a non-empty string is retained; a missing, `null`, blank, or non-string value is treated as unavailable and the helper uses a generic reason based on the run status. The output `error` and `reason` values are strings or `null`; unsupported `run_error` types do not prevent valid transcript rows from being reconciled.

Run statuses are normalized the same way as `select`: uppercase and replace underscores with hyphens. Thus `TIMED_OUT`, `timed-out`, and `TIMED-OUT` resolve to the canonical `TIMED-OUT`; other unrecognized values remain fail-closed. When a submitted post has no matching transcript row, terminal Actor failures (`FAILED`, `ABORTED`, `TIMED-OUT`) produce `run_failed`, even when `dataset_complete` is `false` or `null`; the result preserves canonical run status, dataset completeness value, and available error/reason. `pending` is reserved for nonterminal/unknown Actor states (`READY`, `RUNNING`, `ABORTING`, `TIMING-OUT`, or `UNKNOWN`) and for `SUCCEEDED` runs whose Dataset is explicitly incomplete or has unknown completeness. Every pending result includes a reason that distinguishes waiting for a terminal run state from unresolved Dataset completeness. A successful transcript match remains a match result even when Dataset completeness is false or unknown; it does not establish Dataset completeness. A `duplicate_candidate` reason identifies duplicate submitted candidates and does not reuse a pending/completeness reason.

## Window rules

Anchor the interval to the request timestamp, with an inclusive lower bound and exclusive upper bound. For Daily Scan use [request_time - 24h, request_time); for Weekly Review use [request_time - 7d, request_time). Convert to UTC for Actor filtering if required by the verified schema; filter returned timestamps again against the chosen interval. Display the actual bounds and timezone.

## Report accounting

Use a natural equivalent of “Creator Video Insights” in the user's language as the report title. Per Creator report `returned_raw_rows`, `discovered_returned_in_window`, `type_video_candidates`, `unknown_media_type`, selected, actually processed, successfully transcribed and usable for analysis, omitted due to `per_creator_limit`, each run status, and unprocessed/failed/pending reasons. `discovered_returned_in_window` counts attributable in-window raw rows with usable URLs, including duplicates; `unknown_media_type` counts attributable in-window unknown-type raw rows, including duplicates and without requiring a URL; `type_video_candidates` counts deduplicated usable-URL rows with exact `type == "Video"` before the local cap. Because discovery uses `"skipPinnedPosts": true`, returned rows cannot represent every post in the requested time window; report an excluded-post count only when the Actor provides a verifiable count. Unknown types must never be presented as zero confirmed videos. Do not call a capped set complete. Posts and metrics remain supporting metadata; transcript-grounded analysis is the core report.

The select operation requires the exact output-field map, one bundle per Actor run, and exact run status. `retrieval_complete=true` is valid only with traceable host-provided evidence; a complete empty run is `no_candidates` only when its status is `SUCCEEDED` and completeness evidence establishes that all Dataset pages were read. Missing/null completeness, run success alone, a row count below `resultsLimit`, or no visible truncation marker never establishes complete coverage or reliable zero candidates. The helper preserves validated returned rows when completeness is unknown, marking overall and affected creator coverage `unknown`. Failed (`FAILED`, `ABORTED`, `TIMED-OUT`) Actor runs appear in `run_failures`; successful runs with incomplete/unknown retrieval are expressed by their coverage status, not counted as Actor failures. Active, missing-status, and unrecognized-status runs never establish a complete empty result; the helper preserves run ID, mapped usernames, status, optional error text, returned rows and partial coverage. Valid, attributable video rows returned by a failed or incomplete run remain eligible for transcription, while the affected creator and report stay partial (or unknown when completeness or run status is unknown); rows whose identity or required fields cannot be verified remain unresolved and are not sent for transcription. It reports per-run raw row counts, configured results limits and coverage status before any window filtering; one run reaching its limit only creates a `possible_results_limit_reached` warning. For an unverified multi-username run, per-creator `possible_results_limit_reached` is `null` and additional coverage remains unknown. Missing run metadata yields top-level `partial_interface_error`, an `interface_errors` code and missing-field details. Top-level selection statuses are `complete`, `no_candidates`, `partial`, and `partial_interface_error`; row-level malformed/mapping errors use `interface_error`, and unknown media values use `unknown_media_type`. Identity conflicts remain in `unresolved`, make top-level coverage partial, and reduce only attributable creators' coverage; if an issue cannot be attributed safely, overall coverage is unknown and unrelated creator statuses remain unchanged. Thus `complete` means the returned rows and explicit completeness evidence passed local checks; it is not proof beyond that evidence. Contract-level exceptions exit nonzero with an error object. Reconciliation accepts optional `dataset_complete` (`true`, `false`, or `null`); omitted CLI input becomes `null`. It requires the full submitted list, rows, run_status, the Profile Posts `post_contract`, and a Transcript `transcript_contract` naming URL, code, pk, creator, text, segments, segment text, error, and stable-ID kind for source matching. A reconcile match is not a discovery coverage signal. Conflicting URL, creator and stable-ID evidence yields `identity_conflict`; never use those rows for analysis. Example field-map values must come from the current verified schema; the helper defaults to no aliases.

Keep the default report concise: transcript evidence and analysis are primary; provide a selected video's complete actual transcript only when the user asks to expand it. End with a copyable rerun request containing the accounts, mode, and exact interval used. This is text for the user to reuse, not cross-session memory.
