# Instagram Creator Reels Insights

Use this Skill only for account-based Daily Scan and Weekly Review of user-specified public Instagram accounts. Both modes include post discovery followed by video transcription and analysis of the actual transcript. Do not offer single-URL analysis or a posts-only report. Do not schedule runs, monitor in the background, or claim to remember accounts or transcripts across sessions.

Before each report, read [the workflow contract](references/workflow.md). Use the bundled offline helper at `scripts/workflow.py` for settings validation, UTC window construction, candidate selection/status aggregation, staged budget planning, run-option verification, batch partitioning, and transcript reconciliation. Invoke it with `python3 <skill-directory>/scripts/workflow.py` and one JSON object on stdin; consume its JSON result and treat any nonzero exit or `error` as a stop condition. Do not hand-wave past a helper error. If the host cannot safely execute this helper or provide private in-memory inputs, do not start paid Actors; report the host limitation and offer a reusable prompt only for settings, not as evidence that a report ran.

## First use and saved settings

At first use, ask once for (1) the maximum total USD budget for one complete report execution and (2) the maximum recent videos to inspect per creator. In the same short setup, ask whether the user consents to saving their account list and those settings. Save only if the host supports user-authorized persistence. Otherwise return a reusable prompt containing the settings. Do not ask again during routine runs when the user provides saved settings or that prompt. Only confirm a replacement value when the user asks to change a setting.

Use plain language. Never expose Actor fields or ask the user to configure a budget for each Actor run.

If Apify is not connected, pause before making calls. Tell the user to open the current host's connection or integrations settings and connect Apify there. Never ask them to paste a token, cookie, password, or authorization value into chat.

## Request and modes

- Accept public Instagram usernames or profile URLs, a mode, and optional timezone/report language.
- If the mode is omitted, use Daily Scan. Daily Scan covers the rolling 24 hours before the request. Weekly Review covers the rolling 7 days. Resolve explicit calendar periods in the user's timezone and show exact UTC boundaries used for collection and the displayed timezone.
- First explain that the report has two stages: discovering recent posts, then transcribing qualifying videos and analyzing their spoken content.
- Normalize supplied account names/profile URLs conservatively. Keep a mapping from each requested account to its normalized identity. Reject ambiguous or unsupported input; never broaden to other accounts.

## Execution

1. Verify the live schemas, host tool descriptions, access permissions, pagination/completeness signals, current pricing, and account/Actor limits for apple_yang/instagram-post-scraper and apple_yang/instagram-transcripts-scraper. Do not assume field names, batch sizes, result limits, pricing models, or capabilities from old documentation. Supply the helper an explicit exact-field contract copied from the verified Profile Posts output schema and exact field contract for Transcript output. If the current field map or media-type values cannot be verified, stop with an interface error; never return “no recent videos” for a schema gap.
   The Profile Posts contract must identify the exact creator, URL, timestamp, type, stable-ID fields, stable-ID kind, verified video type values, and verified non-video type values. Unknown media types remain visible and make the selection result an interface error; do not treat them as evidence of zero eligible videos. Before reconciliation, provide both contracts. If their stable-ID kinds differ and no verified mapping exists, stop with an interface error.
2. Before discovery, call helper operation `plan_stage` with `stage: "discovery"`, only the known Profile Posts runs, and the verified host/pricing contracts. Submit only each returned `tool_call.arguments` to the named tool; `planning` is a separate accounting object, never tool input. Use Profile Posts Actor to discover public posts in the requested window. Read all pages and retain returned identity, URL, timestamp, and type.
3. The public Profile Posts schema describes resultsLimit as a maximum result count but does not specify its behavior across multiple usernames. Use one username per Profile Posts run and set that run's retrieval limit independently from the per-creator processing cap. Pass the helper one run bundle per actual run, preserving its run ID, submitted username, exact resultsLimit, every raw returned row, the exact Actor `status` as `run_status`, optional error/status text, and retrieval-completeness evidence. Only `SUCCEEDED` plus a complete dataset read can support a successful discovery result, including a complete zero-candidate result. Preserve rows returned by failed or unfinished runs, but mark their account coverage incomplete; missing or unrecognized run status must fail closed. Do not flatten rows across runs: the helper checks each run's raw row count against that run's limit before local time-window filtering. If run boundaries, limits, status, or account mapping are missing, report unknown coverage and stop any completeness claim. If the run result reaches its limit, report a possible cap and unknown additional candidates, not definite truncation. This makes each run's result set correspond to one creator and adds one discovery run per creator; every run consumes the shared report budget. If live input semantics or output fields do not support reliable accounting, stop rather than claim the cap was enforced. Run the helper's selection operation with the verified output field map; it deduplicates equivalent URLs and retains duplicate/conflicting identity rows with their reasons. Keep raw run IDs and diagnostic fields internal; explain a failed or incomplete discovery to the user in plain language and mark the affected account/report partial.
4. Filter to Reels/videos and the report window using actual returned fields. Per creator, select the newest items up to the agreed processing cap. Report returned candidates, selected, processed, omitted among returned candidates, and any unknown additional candidates per creator; explain retrieval gaps. Keep unresolved identity or interface rows and their reasons. A conflict or row-level interface error prevents a complete coverage claim; attribute it only to creators supported by the row, and report overall coverage as unknown when it cannot be attributed. A capped or incomplete sample is not complete coverage.
5. After discovery, use only the actual selected URLs to create supported Transcript batches. Call `plan_stage` with `stage: "transcription"`, the discovery ledger, and only those now-known runs. Earlier discovery allocations remain reserved at their full caps because the helper has no verified usage readback contract; if the remaining budget cannot cover transcript batch minima/caps, keep discovery results and report the affected posts as unprocessed for budget limits. Do not ask for per-video approval or interrupt for safe internal batching. After a run, verify applied options only through the exact run-readback tool and fields confirmed in this host's live schema. If unavailable or mismatched, stop later paid calls and mark the report partial with budget transmission unverified. Do not retry, add runs, or expand scope to bypass the cap.
6. Pass the complete submitted-candidate set and every returned transcript row to the helper's reconciliation operation. It canonicalizes verified Instagram URL variants and tracking parameters, uses only verified URL/code/pk fields, supports verified ID fallback, and returns a status for every submitted post even when no row was returned. It distinguishes explicit empty text, missing text, malformed rows, segment-only results (preserved without inventing concatenation), duplicate rows, identity conflicts, unmatched rows, and run/Dataset-pending states. Never match by row order.
7. Read all pages before final coverage claims. If submission status is uncertain, a Dataset is incomplete, or a run is active, keep affected items pending/provisional. Never automatically retry, create a replacement run, or spend beyond budget. Preserve confidently matched partial results.

## Analysis and report

Analyze only the Actor's actual transcript text. Keep original transcript distinct from generated summary and analysis. Do not infer visuals, editing, product display, creator intent, audience reaction, or causation. Link each insight to its post URL and quote a short supporting transcript excerpt where useful.

**Daily Scan:** show exact window/timezone; per creator show discovered, selected/processed, omitted, successful, empty, failed and pending counts. For each selected video show URL, publish time, transcript status and, when available, transcript highlights, opening Hook, core point, speaking structure, delivery and closing/CTA. Give a concise, clearly labeled interpretation based on the transcript. Preserve post details and failure status when transcription fails.

**Weekly Review:** show the same coverage accounting. Summarize recurring topics, Hooks, speaking structures and CTAs only from successfully matched transcripts in this report. For every pattern, provide representative post links and transcript evidence. Call out small samples and partial coverage; do not describe them as long-term trends.

Keep the default report readable: show transcript highlights and source-linked analysis, not every full transcript inline. If the user asks to expand a particular video, provide that video's actual returned transcript separately, with its post link, and label it as Actor-returned text rather than generated analysis.

Never treat missing metrics as zero. Engagement counts, if returned, are optional collection-time context only and must not replace or lead the report.

When a report stops at a run cap or host limitation, retain usable results, label the report partial, list what remains and why, and let the user decide whether to change settings in a later request. Do not prompt mid-run to re-confirm or increase the budget.

At the end, include a short copyable request containing the accounts, report mode, and the exact time range just used. This helps the user run it again; do not imply that the Skill will remember settings or prior transcripts in another session.
