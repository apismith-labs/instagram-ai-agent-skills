# Workflow contract

This reference is part of the Skill execution path. Read it before each report and run `python3 <skill-directory>/scripts/workflow.py` with one JSON object on stdin for `settings`, `window`, `select`, `split`, and `reconcile` as applicable. The helper is offline, makes no network calls, and stores no settings. If the host cannot safely execute it or supply private in-memory inputs, explain that host limitation and do not start Actor calls.

## Configuration and user interaction

A report uses the public account list, a positive integer `per_creator_limit`, and whether the user agreed to save the account list and limit. The first setup confirms these items only; do not request a report budget or per-run cost option. Routine requests reuse settings available in the current session or supported, user-authorized storage. Otherwise provide a reusable prompt. For backward compatibility, an older settings object may contain `report_budget_usd`; ignore it and never return or use it.

If Apify is disconnected, stop relevant calls and direct the user to the current host's connection settings. Never request secrets in chat. Be transparent that the report invokes discovery and transcript processing, possibly across multiple runs, and that actual usage follows the user's Apify account and each Actor's current billing rules. Do not estimate or promise fees, or repeatedly interrupt to ask about a budget. The user can inspect actual usage in Apify Console. Follow the host's own approval requirements.

For Daily/Weekly boundaries call `window` with request time and mode. Preserve `end_utc_exclusive` in every later `select` call.

## Host tools and live contracts

Use only tools actually exposed by the selected host and their current live schemas. Do not assume one universal tool name, argument structure, or permission model. Verify the Profile Posts and Transcript inputs/outputs, account identity, pagination/completeness, statuses, and batch behavior before use. If a tool, authorization, or required output contract is missing, stop the affected work and state that specific functional/access blocker. Do not block normal use because `callOptions`, `maxTotalChargeUsd`, `maxItems`, or run-options readback is absent; run-level budget planning and cost controls are outside this Skill's requirements.

## Retrieval and processing limits

The user's per-creator limit applies after discovery. It selects at most that many eligible returned videos for transcript processing and analysis; it does not limit Actor retrieval, guarantee full discovery, or cap cost. If an older saved configuration includes `report_budget_usd`, ignore it.

Use the current Profile Posts schema for its retrieval fields. Do not map `per_creator_limit` to Actor `resultsLimit` unless current evidence verifies the same semantics. The `resultsLimit` field, when required by the Actor input, remains a separate retrieval control. Until its scope, ordering, media inclusion, and completeness behavior are verified, do not claim that it returns the newest N posts or fully scans the time window. If returned coverage cannot be trusted, mark it partial/unknown rather than reporting zero candidates or a complete scan.

## Profile discovery and per-creator cap

Use the requested half-open report interval (inclusive start, exclusive end) and filter results again locally. The `select` helper input is a list of per-run bundles, each with a unique `run_id`, the exact `usernames` submitted to that run, the `results_limit` sent in that run, and all raw returned `posts`. `retrieval_complete` is tri-state: `true` is accepted only with `retrieval_complete_evidence` containing `source` and `detail`; `false` means explicitly incomplete; missing, null, or an unsupported true claim without evidence is unknown. The helper checks only the evidence object's shape and that `source` / `detail` are non-empty strings. It does not authenticate the source or verify the truth of the description. Callers may set `true` only with traceable, real host/Actor evidence establishing completeness. The current Apify plugin has not supplied this Skill with a verified completeness signal; never infer it from `SUCCEEDED`, returned row count, a count below `resultsLimit`, an empty result, or absence of a truncation marker. Unknown completeness does not discard validated returned candidates, but it prevents complete coverage and a reliable `no_candidates` result. The helper compares each run's raw row count with that run's limit before applying the local time-window filter; it never combines counts across runs. Missing run boundaries, limits, or username mappings return `partial_interface_error` with machine-readable missing-metadata details and unknown coverage.

If one run contains multiple usernames and the limit's scope is not verified, the helper marks coverage `unknown_multi_username_limit_scope` or `possible_results_limit_reached_scope_unknown`; it does not divide returned rows or infer per-creator truncation. The Skill should submit one username per run while multi-username semantics remain unverified. Reaching the per-run row limit is only a possible cap signal, not proof of truncation. The public input schema says `resultsLimit` is a maximum result count but does not establish newest-first ordering, whether non-video posts count toward it, or full-window coverage. No single-username results-limit behavior has been empirically verified. A one-username run isolates the configured run limit for accounting, but does not prove recency ordering or complete coverage. The public Output schema lists creator, URL, timestamp, type, shortCode, and pk field names/types, but it does not enumerate media type values or establish runtime completeness. Before processing, verify the current live output contract and media values; otherwise return an interface error and do not claim no posts. A verified runtime contract must explicitly map exact creator, URL, timestamp, media-type and stable-ID fields, stable-ID kind, and exact video and non-video type values. Keep every requested creator represented, including failed/no-match states.

For returned records, use only the exact field mapping supplied from the live output schema; no field-alias guessing. A missing required field is an interface error. Canonicalize verified Instagram post URLs across /reel/ and /reels/, host variants, optional trailing slash and known tracking parameters; preserve unknown query parameters. Detect same-URL duplicates before applying the per-creator cap. Flag URL/creator/stable-ID conflicts rather than merging. Classify out-of-window, verified non-video, unknown media type, and missing-timestamp rows separately. Type matching is case-insensitive against explicitly verified values only; any unknown in-window type makes the selection result an interface error and remains auditable, never a clean zero-candidate result. Unresolved records retain status-specific evidence: identity/interface errors carry a `reason`, while unknown media types carry the actual returned `value` and need not invent a reason. Sort eligible video posts newest first by verified timestamp; records without timestamp remain visible as unresolved and are not silently treated as recent. Preserve validated returned candidates even when discovery completeness is unknown; mark unseen-candidate coverage unknown rather than inferring completeness.

If a bundle omits only its `usernames` mapping but has otherwise valid run metadata, a row may attribute the run only after its contracted creator exactly matches a requested creator and it passes URL, identity-conflict, in-window timestamp, and verified-video checks as a valid processing candidate. The author-level `run_coverage` entry represents this verified candidate-to-run association, not an author guess from an arbitrary row. Selected rows retain the run ID and run index, and overall coverage may be unknown because the run mapping is incomplete. Creator coverage becomes unknown only for a requested creator explicitly attributable through a valid candidate; creators with no such candidate retain their own evidence-based status. This local status does not prove the Actor scanned the full window. Rows that cannot be attributed, or whose required fields/URL are invalid, remain in `unresolved` with the original row, available run ID/index, and a reason; never infer an author from URL, type, or row order. Other malformed bundles retain their rows as unresolved instead of dropping them.

## Transcript batches and reconciliation

Re-read live Transcript Actor schema and account limits. Build batches only from selected, deduplicated URLs and within a batch size supported by the live Actor schema/account. Split batches internally when supported; do not hide calls, automatically retry, or expand scope. Reconcile against the full submitted list so each post gets a result even when the Actor returned no row. Use exact/canonical URL first, then only the verified post ID kind (code or pk); never use result order. Distinguish explicit empty text, missing text, invalid structure, segment-only results and Actor error, no returned row, duplicate rows, identity conflict, unmatched URL and Dataset incompleteness. Preserve valid segments when top-level text is absent, but do not concatenate them unless the live contract proves a safe delimiter. Never interpret missing text as no speech. Do not retry automatically.

A complete transcript Dataset count requires terminal run state plus complete Dataset/page evidence from the host. If unavailable, mark results provisional and report the limitation. `dataset_complete` may be `true`, `false`, or `null`; if the CLI field is omitted, it is treated as `null` (unknown), not as explicit false and not as complete. A `reconcile` row status of `success` means only that the returned transcript row was reliably matched to its submitted post; it says nothing about discovery completeness or whether the transcript Dataset itself was fully read. Every submitted-post result preserves the `dataset_complete` value, including duplicate-row and identity-conflict results. Before reconciliation, pass both verified contracts: `post_contract` and `transcript_contract`. Their stable ID kinds must match unless a specific reliable mapping has been separately verified; this implementation has no such mapping, so a mismatch or missing contract is an interface error before row matching.

For `reconcile`, `run_error` is an optional input containing only the error text or status message actually returned by the host for that same run. Never invent an error or map a message from another run. Only a non-empty string is retained; a missing, `null`, blank, or non-string value is treated as unavailable and the helper uses a generic reason based on the run status. The output `error` and `reason` values are strings or `null`; unsupported `run_error` types do not prevent valid transcript rows from being reconciled.

Run statuses are normalized the same way as `select`: uppercase and replace underscores with hyphens. Thus `TIMED_OUT`, `timed-out`, and `TIMED-OUT` resolve to the canonical `TIMED-OUT`; other unrecognized values remain fail-closed. When a submitted post has no matching transcript row, terminal Actor failures (`FAILED`, `ABORTED`, `TIMED-OUT`) produce `run_failed`, even when `dataset_complete` is `false` or `null`; the result preserves canonical run status, dataset completeness value, and available error/reason. `pending` is reserved for nonterminal/unknown Actor states (`READY`, `RUNNING`, `ABORTING`, `TIMING-OUT`, or `UNKNOWN`) and for `SUCCEEDED` runs whose Dataset is explicitly incomplete or has unknown completeness. Every pending result includes a reason that distinguishes waiting for a terminal run state from unresolved Dataset completeness. A successful transcript match remains a match result even when Dataset completeness is false or unknown; it does not establish Dataset completeness. A `duplicate_candidate` reason identifies duplicate submitted candidates and does not reuse a pending/completeness reason.

## Window rules

Anchor the interval to the request timestamp, with an inclusive lower bound and exclusive upper bound. For Daily Scan use [request_time - 24h, request_time); for Weekly Review use [request_time - 7d, request_time). Convert to UTC for Actor filtering if required by the verified schema; filter returned timestamps again against the chosen interval. Display the actual bounds and timezone.

## Report accounting

Per creator expose discovered candidates, eligible timestamped videos, selected for transcription, successfully transcribed and usable for analysis, omitted due to per-creator cap, and unprocessed/failed/pending with reasons. Do not call a capped set complete. Posts and metrics remain supporting metadata; transcript-grounded analysis is the core report.

The select operation requires the exact output-field map, one bundle per Actor run, and exact run status. `retrieval_complete=true` is valid only with traceable host-provided evidence; a complete empty run is `no_candidates` only when its status is `SUCCEEDED` and completeness evidence establishes that all Dataset pages were read. Missing/null completeness, run success alone, a row count below `resultsLimit`, or no visible truncation marker never establishes complete coverage or reliable zero candidates. The helper preserves validated returned rows when completeness is unknown, marking overall and affected creator coverage `unknown`. Failed (`FAILED`, `ABORTED`, `TIMED-OUT`) Actor runs appear in `run_failures`; successful runs with incomplete/unknown retrieval are expressed by their coverage status, not counted as Actor failures. Active, missing-status, and unrecognized-status runs never establish a complete empty result; the helper preserves run ID, mapped usernames, status, optional error text, returned rows and partial coverage. Valid, attributable video rows returned by a failed or incomplete run remain eligible for transcription, while the affected creator and report stay partial (or unknown when completeness or run status is unknown); rows whose identity or required fields cannot be verified remain unresolved and are not sent for transcription. It reports per-run raw row counts, configured results limits and coverage status before any window filtering; one run reaching its limit only creates a `possible_results_limit_reached` warning. For an unverified multi-username run, per-creator `possible_results_limit_reached` is `null` and additional coverage remains unknown. Missing run metadata yields top-level `partial_interface_error`, an `interface_errors` code and missing-field details. Top-level selection statuses are `complete`, `no_candidates`, `partial`, and `partial_interface_error`; row-level malformed/mapping errors use `interface_error`, and unknown media values use `unknown_media_type`. Identity conflicts remain in `unresolved`, make top-level coverage partial, and reduce only attributable creators' coverage; if an issue cannot be attributed safely, overall coverage is unknown and unrelated creator statuses remain unchanged. Thus `complete` means the returned rows and explicit completeness evidence passed local checks; it is not proof beyond that evidence. Contract-level exceptions exit nonzero with an error object. Reconciliation accepts optional `dataset_complete` (`true`, `false`, or `null`); omitted CLI input becomes `null`. It requires the full submitted list, rows, run_status, the Profile Posts `post_contract`, and a Transcript `transcript_contract` naming URL, code, pk, creator, text, segments, segment text, error, and stable-ID kind for source matching. A reconcile match is not a discovery coverage signal. Conflicting URL, creator and stable-ID evidence yields `identity_conflict`; never use those rows for analysis. Example field-map values must come from the current verified schema; the helper defaults to no aliases.

Keep the default report concise: transcript evidence and analysis are primary; provide a selected video's complete actual transcript only when the user asks to expand it. End with a copyable rerun request containing the accounts, mode, and exact interval used. This is text for the user to reuse, not cross-session memory.
