# Workflow contract

This reference is part of the Skill's execution path. Read it before every report and run `python3 <skill-directory>/scripts/workflow.py` with one JSON object on stdin for `settings`, `window`, `select`, `plan_stage`, `verify_run`, `remaining`, `split`, and `reconcile` operations as applicable. The helper makes no network calls, starts no Actor, and stores no settings. If Python/private execution or a required verified schema, pricing, host call, or run-readback contract is unavailable, stop before paid calls and report the exact blocker.

## Configuration

A report requires a positive finite report_budget_usd, a positive integer per_creator_limit, the public account list, and an explicit record of whether the user consented to persistence. Store nothing unless both consent and host-supported storage are confirmed. A reusable prompt is the fallback. If Apify is disconnected, stop and direct the user to the host's connection settings; never request secrets in chat.

Invoke the settings operation with that configuration before planning. For Daily/Weekly boundaries call window with the request timestamp and mode. Preserve its end_utc_exclusive output in every later select call.

## Per-report budget and two-stage planning

Do not start a paid run until the selected host's live tool catalog and schemas confirm `call-actor` accepts `actor`, `input`, `waitSecs`, and `callOptions`, and a tool actually exposed by that host returns the applied options for the exact run ID. Do not presume `get-actor-run` returns `options`, or that the optional `get-actor-run-list` is loaded. Apify's current public tool reference documents `call-actor` run limits and a 0–45 second `waitSecs`, but public documentation alone is not proof of this host's live schema or response shape. `waitSecs` is only how long the tool waits for the run response; it is not an Actor execution-time limit or a fee cap.

Plan in two stages. Before discovery, run `plan_stage` with `stage: "discovery"`, the validated report settings, only known Profile Posts runs and the verified host/pricing contracts. Each descriptor has two sibling fields: `tool_call` contains the tool name and only its `arguments`; `planning` contains the billing model, conservative allocation and full reservation. Send only `tool_call.arguments` to the tool. No transcript URLs or speculative Transcript runs belong in this stage. The helper reserves each discovery run's full cap against the report's total budget.

After discovery and selection, construct Transcript runs from the actual selected URLs and live-supported batch size. Call `plan_stage` with `stage: "transcription"` and the discovery ledger. Every prior discovery run remains reserved at its maximum allocation; this helper has no verified usage readback and does not return unused amounts to the pool. If the safe Transcript allocations do not fit in the unreserved remainder, keep discovery output and report the affected videos unprocessed for budget limits. Do not retry, add runs, or expand scope. Replanning with an invalid ledger, wrong budget, duplicate stage, or missing discovery stage fails closed.

For a verified pay-per-result Actor, compute a conservative USD reserve from current verified pricing and the requested billable item count, and pass `callOptions.maxItems`; this differs from Actor input `resultsLimit`, and does not guarantee the Actor returns no more than that many rows. For a verified pay-per-event Actor, pass the positive allocation as `callOptions.maxTotalChargeUsd`. Do not pass both as generic double protection. The official Apify MCP README says to use `maxItems` for pay-per-result and `maxTotalChargeUsd` for pay-per-event; never embed example prices as current facts.

The public Apify MCP README documents `call-actor` `callOptions` with `maxItems` or `maxTotalChargeUsd`, but this Codex session exposes no Apify tools, so no target-host live schema is verified. The official [v0.16.0 release notes](https://github.com/apify/apify-mcp-server/releases/tag/v0.16.0), released 2026-09-17, list commit [`5264fe6`](https://github.com/apify/apify-mcp-server/commit/5264fe6) and say an `actorId` filter was added to `get-actor-run-list`; official [issue #1351](https://github.com/apify/apify-mcp-server/issues/1351) also lists the filter and its PR as merged. This supports the released Actor-filter feature. WorkBuddy's 2026-11-06 read-only review reports that the corresponding implementation declares optional `actorId`. The commit/tag source file was not readable in this check, so this reference does not independently claim its exact input type/schema or that the target host exposes it; a previously cached `master` source snippet is not evidence that current source lacks the parameter. `actorId` is an input filter, not an output field, and does not establish run-options availability. The declared run-list output is a paginated envelope with item fields such as `id`, `actId`, `status`, storage IDs and `usageTotalUsd`, but not `options`. The implementation may pass the Apify client's `runs().list(...)` result through raw text and `structuredContent`; this does not prove an actual upstream object contains `options` or that a host exposes undeclared fields. By contrast, `get-actor-run` builds a curated response object whose reviewed schema does not include run `options`. Neither tool is a verified options readback path for this Skill. The current Codex live catalog exposes neither tool nor `call-actor`. Keep budget execution blocked until the selected host's live schemas and actual response shape establish both call-option forwarding and exact-run options readback. Synthetic fixtures prove only offline comparison logic, not host forwarding, Apify enforcement, or charges.

## Profile discovery and per-creator cap

Use the requested half-open report interval (inclusive start, exclusive end) and filter results again locally. The `select` helper input is a list of per-run bundles, each with a unique `run_id`, the exact `usernames` submitted to that run, the `results_limit` sent in that run, all raw returned `posts`, and explicit `retrieval_complete` evidence. The helper compares each run's raw row count with that run's limit before applying the local time-window filter; it never combines counts across runs. Missing run boundaries, limits, or username mappings return `partial_interface_error` with machine-readable missing-metadata details and unknown coverage.

If one run contains multiple usernames and the limit's scope is not verified, the helper marks coverage `unknown_multi_username_limit_scope` or `possible_results_limit_reached_scope_unknown`; it does not divide returned rows or infer per-creator truncation. The Skill should submit one username per run while multi-username semantics remain unverified. Reaching the per-run row limit is only a possible cap signal, not proof of truncation. The public input schema says `resultsLimit` is a maximum result count but does not establish newest-first ordering, whether non-video posts count toward it, or full-window coverage. No single-username results-limit behavior has been empirically verified. A one-username run isolates the configured run limit for accounting, but does not prove recency ordering or complete coverage. The public Output schema lists creator, URL, timestamp, type, shortCode, and pk field names/types, but it does not enumerate media type values or establish runtime completeness. Before processing, verify the current live output contract and media values; otherwise return an interface error and do not claim no posts. A verified runtime contract must explicitly map exact creator, URL, timestamp, media-type and stable-ID fields, stable-ID kind, and exact video and non-video type values. Keep every requested creator represented, including failed/no-match states.

For returned records, use only the exact field mapping supplied from the live output schema; no field-alias guessing. A missing required field is an interface error. Canonicalize verified Instagram post URLs across /reel/ and /reels/, host variants, optional trailing slash and known tracking parameters; preserve unknown query parameters. Detect same-URL duplicates before applying the per-creator cap. Flag URL/creator/stable-ID conflicts rather than merging. Classify out-of-window, verified non-video, unknown media type, and missing-timestamp rows separately. Type matching is case-insensitive against explicitly verified values only; any unknown in-window type makes the selection result an interface error and remains auditable, never a clean zero-candidate result. Sort eligible video posts newest first by verified timestamp; records without timestamp remain visible as unresolved and are not silently treated as recent. Pass an explicit retrieval_complete flag. If false, the helper reports only candidate rows actually returned and marks additional unseen candidates unknown; it cannot invent a complete discovered count from a truncated result.

## Transcript batches and reconciliation

Re-read live Transcript Actor schema and account limits. Build batches only from selected, deduplicated URLs and only within the report budget. Reconcile against the full submitted list so each post gets a result even when the Actor returned no row. Use exact/canonical URL first, then only the verified post ID kind (code or pk); never use result order. Distinguish explicit empty text, missing text, invalid structure, segment-only results and Actor error, no returned row, duplicate rows, identity conflict, unmatched URL and Dataset incompleteness. Preserve valid segments when top-level text is absent, but do not concatenate them unless the live contract proves a safe delimiter. Never interpret missing text as no speech. Do not retry automatically.

A complete transcript coverage count requires terminal run state plus complete Dataset/page evidence from the host. If unavailable, mark results provisional and report the limitation. Before reconciliation, pass both verified contracts: `post_contract` and `transcript_contract`. Their stable ID kinds must match unless a specific reliable mapping has been separately verified; this implementation has no such mapping, so a mismatch or missing contract is an interface error before row matching.

## Window rules

Anchor the interval to the request timestamp, with an inclusive lower bound and exclusive upper bound. For Daily Scan use [request_time - 24h, request_time); for Weekly Review use [request_time - 7d, request_time). Convert to UTC for Actor filtering if required by the verified schema; filter returned timestamps again against the chosen interval. Display the actual bounds and timezone.

## Report accounting

Per creator expose discovered candidates, eligible timestamped videos, selected for transcription, successfully transcribed and usable for analysis, omitted due to per-creator cap, and unprocessed/failed/pending with reasons. Do not call a capped set complete. Posts and metrics remain supporting metadata; transcript-grounded analysis is the core report.

The select operation requires the exact output-field map, one bundle per Actor run, exact run status, and explicit retrieval completeness evidence. A complete empty run is a valid `no_candidates` result only when its run status is `SUCCEEDED` and all dataset pages were read. Failed (`FAILED`, `ABORTED`, `TIMED-OUT`), active/unfinished, missing-status, and unrecognized-status runs never establish a complete empty result; the helper preserves run ID, mapped usernames, status, optional error text, returned rows and partial coverage. It reports per-run raw row counts, configured results limits and coverage status before any window filtering; one run reaching its limit only creates a `possible_results_limit_reached` warning. For an unverified multi-username run, per-creator `possible_results_limit_reached` is `null` and additional coverage remains unknown. Missing run metadata yields top-level `partial_interface_error`, an `interface_errors` code and missing-field details. Top-level selection statuses are `complete`, `no_candidates`, `partial`, and `partial_interface_error`; row-level malformed/mapping errors use `interface_error`, and unknown media values use `unknown_media_type`. Identity conflicts remain in `unresolved`, make top-level coverage partial, and reduce only attributable creators' coverage; if an issue cannot be attributed safely, overall coverage is unknown and unrelated creator statuses remain unchanged. Thus `complete` means the returned rows and successful run evidence passed local checks; it is not proof the Actor scanned the entire requested time window. Contract-level exceptions exit nonzero with an error object. The reconcile operation requires the full submitted list, rows, run_status, dataset_complete, the Profile Posts `post_contract`, and a Transcript `transcript_contract` naming URL, code, pk, creator, text, segments, segment text, error, and stable-ID kind for source matching. Conflicting URL, creator and stable-ID evidence yields `identity_conflict`; never use those rows for analysis. Example field-map values must come from the current verified schema; the helper defaults to no aliases.

Keep the default report concise: transcript evidence and analysis are primary; provide a selected video's complete actual transcript only when the user asks to expand it. End with a copyable rerun request containing the accounts, mode, and exact interval used. This is text for the user to reuse, not cross-session memory.
