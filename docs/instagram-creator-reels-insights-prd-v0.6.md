**文档状态：** 产品需求草案，供产品范围确认与实现准备
**项目：** Instagram AI Agent Skills
**工作名称：** Instagram Creator Reels Insights
**展示名称候选：** Instagram Creator Reels Insights（需在发布前检查搜索词与目录命名；“competitor analysis”保留为常见使用场景和搜索词，不限定用户只能研究竞品）
**建议 Skill slug：** `instagram-creator-reels-insights`（待搜索与可用性核查）
**版本：** 0.6
**日期：** 2026-11-05
**目标用户：** 会重复研究一组公开 Instagram 账号的创作者、品牌营销人员、社媒运营和代理机构

> 本 PRD 定义一个拟议 Skill 的产品需求，不表示 Actor 集成、Skill 实现或平台流程已经验证。Daily Scan / Weekly Review 是用户发起的报告模式，不代表自动定时或后台监控。

## 本版变更

相较 v0.5，本版按产品目标统一预算口径：用户只在首次设置时确认每次日报/周报执行的总预算上限，以及每位作者每份报告的作品数上限；日常调用复用设置，不再重复询问。单个 Actor run 的 Apify 费用参数属于内部实现，Skill 负责把整份报告的预算分配到所有 run 并确保总上限；实现前须验证宿主能否传递该参数。V1 仍只做指定账号的日报/周报 transcript 分析。

## 1. 产品目标与价值主张

本 Skill 帮用户按需检查自己指定的公开 Instagram 创作者账号，发现近期视频，取得口播转录，并基于真实转录分析创作者如何开场、展开观点和引导行动。竞品研究是重要场景之一，也可用于关注创作者、品牌账号或内容灵感来源。

产品价值应能用一句普通用户听得懂的话说明：

> 关注你指定的 Instagram 创作者，获取近期 Reels 的口播转录，并按天或按周整理可追溯的内容洞察。

本项目从四个目标评估设计：

1. **容易找到和理解：** Skill 名称、简介、README 与示例请求直说适用对象、输入和结果；不要求用户先理解 Actor、schema 或内部实现。
2. **提高有效转化：** 用户能从发现 Skill、安装、连接 Apify 到第一份可用报告；安装与 Apify 授权分开说明，缺少连接时提供清晰下一步。
3. **促进持续使用：** 日报与周报解决重复研究任务；首次使用时确认每次报告的总预算、每位作者作品上限和账号清单等设置，经用户许可保存后复用；每次报告完成后提供可复用的下一次请求。
4. **产生可持续调用：** 每份报告都以用户明确请求的转录分析提供价值，实际调用对用户透明。调用量是用户持续获得价值后的结果，不以隐藏调用或无价值的重复运行来增加。

## 2. 产品假设与成功观察

核心假设：当用户能以简单请求反复获得指定账号近期 Reels 的口播证据和实用分析时，他们会继续运行 Daily Scan 或 Weekly Review，并形成可持续的 Transcript Actor 使用。

在小规模试用中观察：

- 新用户是否能理解 Skill 能做什么、需要什么输入，以及 Apify 连接是独立前置条件；
- 从安装/选择到第一份含有效转录和来源链接的报告，是否需要额外人工指导；
- 用户是否再次运行日报或周报，以及重复使用的时间间隔和模式；
- 候选视频中成功取得并可用于分析的转录覆盖情况及主要失败原因；
- 来源链接、转录和洞察的对应是否稳定，用户是否会把洞察用于后续内容研究；
- 每份报告实际发生的 Profile Posts 与 Transcript Actor 调用和转录处理量，用于理解真实使用模式。

这些是试用观察项，不是当前已有遥测能力或预设发布指标。可通过用户反馈，或经用户知情授权的汇总记录观察；不默认进行隐蔽跟踪、用户画像或跨会话数据收集。不预设目标数字。不能单独用调用量判断成功，需结合用户复用、转录可用率、来源对应质量和报告价值。

## 3. 用户与任务

### 3.1 目标用户

- **独立创作者：** 定期研究同赛道创作者近期如何开场、表达观点和做 CTA。
- **品牌与营销人员：** 用来源可追溯的口播材料准备内容研究或团队简报。
- **社媒运营团队：** 对一组公开账号反复运行日报或周报，发现内容模式和选题线索。
- **社媒代理机构：** 为客户指定账号整理逐条可核对的转录和内容洞察。

### 3.2 主要任务

- “扫描这些账号过去 24 小时的 Reels，转录后告诉我每条视频如何开场、讲了什么、怎样收尾。”
- “复盘这些账号最近 7 天的口播，找出重复出现的主题、Hook、结构和 CTA，并链接到原帖。”

V1 不提供独立的指定视频 URL 分析模式，也不提供跳过转录的“仅看帖子数据”模式。所有日报和周报都以账号扫描为入口，并默认包含符合范围的视频转录和基于 transcript 的内容分析。

## 4. V1 范围

### 4.1 目标

1. 提供用户发起的 Daily Scan 与 Weekly Review，两者默认包含候选发现、视频转录和口播分析。
2. 用户提供至少一个公开账号；未指定周期时默认 Daily Scan（最近 24 小时滚动窗口），明确要求 Weekly Review 时使用最近 7 天。只在账号或授权等关键输入缺失时追问。
3. 将每条帖子、转录和洞察对应到实际账号、帖子 URL 与发布时间。
4. 默认简洁呈现转录要点和分析；用户需要时可展开完整转录。
5. 处理部分成功、失败和限制时保留有效结果，说明覆盖范围和下一步。
6. 支持用户低摩擦重复运行；在宿主支持且用户同意时保存账号清单、预算和每位作者作品上限等运行设置，但不保存 transcript 库或历史报告。明确说明没有内容历史时窗口重叠和重复内容的可能性。

### 4.2 非目标

- 自动判断哪些账号是用户的竞品；账号由用户指定。
- V1 自动定时、后台监控、通知、推送、持久转录库或历史趋势。
- 以单条视频 URL 为入口的独立分析，以及跳过转录的纯帖子/指标报告。
- 私有账号或需登录才能访问的内容；绕过访问控制、限流或平台保护。
- 基于 transcript 声称分析视频画面、剪辑、人物、产品画面、评论或观众反应。
- 用一次互动数据快照认定爆款、异常表现、内容质量、增长或因果。
- 承诺固定账号数、处理量、调用次数、识别准确率、费用或效果提升。
- 修改第一个 Instagram Transcript Extractor Skill 的范围和实现。

## 5. 发现、理解与转化旅程

用户路径应尽量短且每一步给出明确下一步：

1. **发现：** 在平台目录、README 或 Skill 列表中，通过清晰名称和自然语言简介判断“这是用来研究指定 Instagram 创作者 Reels 口播的 Skill”。发布前检查用户实际会搜索的词，如 Instagram competitor analysis、Reels transcript、creator content research；不得堆砌关键词或声称搜索排名。
2. **理解：** 页面说明用户需要公开账号、报告时间窗和可用的 Apify 连接；输出是带来源的转录摘要、Hook、主题、结构和 CTA 分析。
3. **安装/选择：** 安装方法跟随所选宿主指南。不要暗示安装 Skill 会自动配置 Apify。
4. **首次使用：** 用户提供账号后，Skill 用一次简短设置确认每次日报/周报执行的总预算上限和每位作者每份报告的作品上限，并确认是否保存账号清单/设置。确认后启动默认日报；说“周报”或给出时间范围即可切换。后续报告复用已确认设置，不重复询问。
5. **报告后复用：** 提供一个可以直接复制的“按相同账号再做一次日报/周报”请求，包含本次账号和偏好；这只是用户可保存的文本，不代表 Skill 会记住账号。

安装和 Apify 授权是两件事。若缺少授权，告诉用户到当前宿主的连接设置完成授权；不要求聊天粘贴 Token、Cookie、session ID 或密码。首次设置时说明一份报告会经过帖子发现和 transcript 两个阶段，可能启动多个 Actor run；用户设置的是整份报告的总费用上限，内部会分配到所有 run。不估算费用，提示用户可在 Apify Console 查看运行和用量。

### 5.1 Skill 名称与简介要求

- 名称先表达 Instagram/Reels 和 competitor/creator research 的任务，不用只有“Insights”这类抽象词。
- 简介应说明：用户指定公开账号；支持日报/周报；默认提取近期 Reels 口播并给出可追溯分析；需要宿主可用的 Apify 连接。
- 简介包含可触发的自然语言意图，例如“分析这些 Instagram 创作者近期 Reels 的转录和口播结构”。
- 发布前在目标目录核查类似名称和搜索词；核查结果用于取舍，不能据此承诺会被搜到。

## 6. 报告模式和输入

### 6.1 账号扫描模式（核心）

必需输入：至少一个公开 Instagram 用户名或主页 URL。用户可指定 Daily Scan、Weekly Review 或明确时间范围；未指定时默认使用 Daily Scan（最近 24 小时滚动窗口），并在报告中显示实际起止时间，不为选择日报/周报增加一次追问。

可选输入：用户时区和报告语言。

首次运行设置：每次日报/周报（一次 Skill 执行）的总预算上限（USD）和每位作者每份报告最多检查的视频数。用日常语言在一次简短问题中确认这两个值，以及用户是否同意保存账号清单和设置；不向用户展示 `maxTotalChargeUsd`、`resultsLimit` 等接口字段，也不把报告语言、Pinned 内容等次要选项塞进初始设置。

只在宿主支持且用户同意时保存最少必要设置；不能持久保存时，生成携带账号和上限的可复用请求，避免同一会话重复询问。

账号、时间窗内符合范围的视频默认进入转录和分析；用户不需要配置转录开关、逐条挑选或填写复杂筛选项。

默认时间范围：

| 模式 | 默认范围 | 主要报告任务 |
|---|---|---|
| Daily Scan（默认） | 请求时点前最近 24 小时 | 逐条呈现窗口内候选视频转录状态和可用的口播分析 |
| Weekly Review | 请求时点前最近 7 天 | 基于本周实际取得的转录归纳重复主题、Hook、表达结构、CTA 和差异 |

默认是滚动窗口，不是自然日或自然周。用户说“今天”“上周”等自然周期时，按用户时区解释并展示具体起止时间。宿主不能确认时区时，询问或明确使用 UTC。Actor 的日期筛选按 live schema 实际行为转换；结果侧仍按用户要求的窗口校验。

## 7. 默认调用与候选选择

### 7.1 首次设置与日常调用

- 首次调用前，用一个简短问题同时确认每次报告执行的总预算上限（USD）、每位作者每份报告的作品数上限，以及用户是否同意保存设置。后续在已保存设置或用户提供的可复用请求可用时直接执行，不重复询问。
- 对用户使用“每份日报/周报最多花费多少”“每位作者最多检查多少条近期视频”等直白说法；API 参数名只留在实现说明中。
- 明确说明一份报告会先发现账号作品，再对符合上限的视频提取 transcript 并分析；可能启动多个 Actor run；用户设置的是**整份报告这一次执行的总预算上限**，不是让用户分别配置每个内部 run。
- 用户请求 Daily Scan/Weekly Review 即授权按已确认设置运行默认流程；不逐条询问，也不在发现阶段和转录阶段之间停下来要求用户确认。若 Actor 的技术批次限制可通过内部拆分多个 run 在用户报告总预算内满足，就由 Skill 自行拆分，不打断用户。
- 对每位作者严格应用已确认的作品上限；默认优先取时间窗内最新作品。最终报告简要列出发现数、处理数和因上限未处理数，不把截取样本描述成该账号的全部作品。
- `maxTotalChargeUsd` 是 Apify 启动 Actor run 时的运行选项，不是 Actor 输入字段。只有宿主调用接口确实暴露并传递该参数时，才可把预算称为硬上限。若当前宿主不支持，不能向用户承诺预算上限有效，也不能启动付费执行；这是实现必须先解决的集成条件，不应转化为日常运行时反复打断用户的选择题。
- 实现必须将报告预算分配给整条执行链路中的所有 Actor run：各 run 的预算分配总和不得超过用户设置的报告总上限；若顺序执行，可依据已发生费用计算后续 run 的剩余预算。若某个 run 达到分配额度，或本次执行预算已用尽，保留已取得结果并标为部分完成；不自动重试或另起 run 绕过用户设置。报告请求即使扩大了账号或时间范围，也沿用已确认的总预算和每作者上限；预算不足时返回部分结果，不在运行中追问。只有用户主动要求更改已保存的预算或作品上限时，才确认并更新设置。
- 尊重宿主原生审批要求；预算设置不能替代宿主要求的审批。

不得猜测 Actor 字段含义或费用，不得隐藏转录调用、超过用户确认的预算/每作者作品上限，也不得为了增加调用量而进行无关重复调用。

### 7.2 候选视频规则

1. 按用户指定的公开账号和报告时间窗发现符合范围的视频；帖子 URL、发布时间和类型用于校验候选与追溯来源。
2. 依据首次设置的每位作者作品上限，默认转录最新的符合范围视频；不要求用户逐条挑选。
3. 不使用互动指标决定转录优先级。若用户另行保存了筛选偏好，只能在用户明确设置后应用，并在报告中说明。
4. 每次报告给出候选总数、每位作者实际提交转录数、已处理数、因用户上限未处理数与失败原因。运行未完成或 Dataset 未完整读取时，标记为部分/暂定，不声称完整覆盖。

## 8. 数据来源和能力边界

### 8.1 拟议 Actor 角色（均须实现前核验）

| 名称 | 拟议职责 | 当前证据状态 |
|---|---|---|
| `apple_yang/instagram-post-scraper`（Profile Posts Actor） | 使用 `usernames`、报告时间窗和用户确认的作品上限发现公开账号的候选视频 | 当前输入页把 `usernames` 与 `resultsLimit` 标为必填，后者描述为返回结果的最大数量；文档没有明确它对多用户名是总上限还是每账号上限。批量账号行为、输出身份字段和分页完整性仍待实测；不得将每作者限额映射到 `resultsLimit` 后未经验证就宣称生效 |
| `apple_yang/instagram-transcripts-scraper`（Transcript Actor） | 对账号发现得到的符合条件视频执行转录，返回 Actor 实际提供的文本、时间戳、状态或错误 | 当前输入页有 `bulkUrls`，并说明免费账户每 run 最多 5 条、付费账户 unlimited；`enhancedcrawl` 成功取回时可能额外计费。账户、平台和 Actor 页面描述均可能变化，批量和跨 Actor 关联流程仍需实现前重新核验 |

Transcript Actor 只负责其实际 schema 支持的转录处理和返回数据。Hook、主题、结构、CTA、摘要与创作启发由 Skill 基于实际 transcript 生成，不能归为 Actor 输出。

### 8.2 实现前需要核实

重新检查两个 Actor 的 live 输入/输出 schema、账号身份匹配字段、时间筛选行为、多账号/多 URL 批量支持、分页读取和 Dataset 完整性信号、状态/错误字段、授权与宿主工具限制。验证 `resultsLimit` 在多用户名时的作用范围；如不是每作者上限，确定可准确执行每作者作品数设置的调用策略。不得根据旧文档猜测字段名、条数、run 上限、费用或可用工具。

Apify 的 `maxTotalChargeUsd` 属于启动 run 的选项，不属于 Actor input schema。Apify API 文档说明它用于限制单次 run 的总费用。目标宿主必须证明能把内部计算出的 run 额度传给每个相关 run；不能只把用户的报告总预算写在 Skill 文本中。当前专用 Apify 工具是否暴露该参数须在选定平台核验。未能执行硬预算上限前，不得把该设置描述为已生效，也不得以预算受控为由启动付费 run。

本轮可见的专用 Transcript Actor 工具参数包含 Actor 输入字段和 `waitSecs`，没有 `maxTotalChargeUsd`。若最终选择这类接口，需要改用或补充能传递 Apify run 选项的调用方式，预算上限才能成为真实护栏。

当前调用、权限、批量和费用限制未知时，PRD 中只保留待验证项；在完成验证前不写入用户文档为事实。

## 9. 核心工作流

### 9.1 账号扫描 Daily/Weekly

```text
识别账号、模式、时间窗和用户偏好
→ 首次使用时确认每份报告的总预算、每作者作品上限及设置保存方式
→ 内部确认 Apify 授权与宿主能够执行整份报告预算
→ 运行 Profile Posts Actor 发现候选并完整读取
→ 按实际账号身份、URL、时间窗和内容类型核验结果
→ 按保存的每作者上限选取最新候选
→ 调用 Transcript Actor 并完整读取
→ 按确切 URL/可靠身份关联 transcript
→ 基于实际 transcript 生成报告，列出覆盖/未处理情况和下次可复制请求
```

### 9.2 结果状态和来源关联

- 每条帖子和转录按实际返回的账号身份、确切 URL 或可靠 ID 对应；绝不按 Dataset 顺序猜测。
- 身份冲突、URL 不匹配或重复候选须保留并标记待核验，不静默删除或强行配对。
- 区分成功转录、空转录/无语音、Actor 错误、账号失败、部分结果、Dataset 未完整、URL 无法匹配和缺少时间戳。
- 即使单条转录失败，也保留该帖子、来源链接和失败状态；不让单条失败抹去其他成功结果。
- 缺失字段与数值 0 不同。没有匹配到结果不代表账号没有发布。
- 区分 Actor 实际返回的原始 transcript 与 Skill 生成的摘要、分析和解释。
- Transcript 只支持口播分析；不得据此推断画面、剪辑、产品展示、人物或观众反应。

## 10. 报告体验

### 10.1 Daily Scan

对每个候选视频显示原帖链接、账号、时间、类型和转录状态。对成功转录的视频给出可读的重点/摘要、Hook、主题与观点、结构、表达方式和 CTA，并提供基于原文的简短创作启发。启发应标为分析或假设，并链接到依据帖子；不要求用户阅读完整长转录才能获得价值。

### 10.2 Weekly Review

以本周实际取得且能关联到来源的 transcript 为基础，整理重复出现的主题、Hook、结构、论点展开、表达方式和 CTA，说明内容差异，提出可测试的创作方向。每个归纳都回链到帖子和 transcript 证据。样本不足、结果不完整或失败较多时，收窄结论并报告覆盖。

### 10.3 完整转录

默认提供逐条重点/摘要和分析，不逐条展开全部长文本。用户可要求展开指定视频的完整实际转录；原始文本与生成分析分开呈现并保留来源链接。完整转录是分析核心数据，不是可选功能。

### 10.4 帖子数据边界

帖子 URL、发布时间和视频类型用于确认候选范围、标注来源和追溯 transcript。点赞、评论、播放量等只有在实际返回时才可作为轻量上下文；默认不用于决定转录优先级，也不作为独立分析报告。缺失值不补 0；不以单次快照推断增长、趋势、爆款、异常、质量、账号排名或因果；不让指标表格挤压 transcript 分析。

## 11. 促进重复使用

- 日报与周报解决不同的重复任务：Daily Scan 快速检查短窗口内的新口播，Weekly Review 总结一周内实际取得的转录模式。
- 报告完成后提供简短、可复制的再运行请求，带上本次账号、模式与偏好，降低用户重新整理输入的成本。
- 把建议用户保存的文本称为“可复用请求”或“账号清单模板”，不能称为 Skill 已保存偏好。
- 用户首次确认后，可在宿主支持且用户同意时保存最少必要的账号清单、预算和每作者作品上限等运行设置；不保存 transcript 或历史报告。宿主不支持保存时，提供一段携带设置的可复用请求，后续用户复制即可继续，不要求逐次重新完成设置问答。
- 滚动窗口重叠时同一帖子可能再次出现。V1 不声称“只展示上次后新增内容”，不做跨报告去重或趋势比较。
- 不用自动重复调用、隐藏定时、空内容重试或无分析价值的重复 run 来提高 Actor 用量。

## 12. README 与目录内容要求

第二项 Skill 实际实现并可检查后，README/Skill 页面需帮助新用户迅速回答：

1. 这个 Skill 监测谁、处理什么内容、输出什么；
2. 需要准备什么（公开账号、宿主中的 Apify 授权，以及首次设置的每份报告总预算和每作者作品上限）；
3. 如何用账号请求日报或周报；
4. 安装 Skill 与连接 Apify 是两个步骤；
5. 如何查看候选覆盖、成功转录、失败项和真实 API 用量。

至少提供可复制示例：Daily Scan 和 Weekly Review。示例语言面向全球用户，报告语言可配置，不设中文默认。用户设置好每次报告的总预算和每作者上限后，示例应展示日常调用不再逐条确认；不要把内部 run 预算分配暴露成用户要管理的设置。只展示账号监测、转录和 transcript 分析主流程，不加入单条视频分析或仅帖子数据等旁支功能。仅列出已实现并经过验证的安装方式和能力；README 是用户指南，不堆放内部测试状态，详细证据放项目测试文档。

名称、简介和示例可用自然搜索词帮助发现，但不承诺目录收录、排名或自动触发。第一版 README 应突出一次报告能解决的问题和需要的输入，不先用 Actor/schema 术语劝退用户。

## 13. 安全、授权与费用说明

- 只处理用户指定的公开账号/视频并遵守平台、Apify 和宿主规则。
- 不绕过登录、访问限制、限流或其他保护；不索取或输出 token、cookie、session ID、密码或授权头。
- 使用用户自己的 Apify 授权连接。首次设置时说明报告包含帖子发现与 transcript 两阶段，以及一份报告可能涉及多个内部运行；日常报告按已确认的整份报告总预算直接运行，结果中呈现实际处理数和失败项。
- 不写固定费用或免费承诺；建议用户查看自己的 Apify Console。工具/宿主要求审批时遵循其审批流程。
- 只在用户明确同意且宿主支持时保存运行所需的账号清单、预算与每作者作品上限；不存储持久账号画像、transcript 库或历史报告。

## 14. 验收标准

### 14.1 发现与首次成功

- 未接触项目的新用户可从简介理解这是用于分析指定 Instagram 创作者 Reels 口播的 Skill，并能找到可复制的日报/周报请求。
- 安装和 Apify 授权步骤区分清楚；未连接时给出宿主对应的下一步，不要求用户把凭据粘贴到聊天。
- 以一条或一组公开账号发起 Daily Scan/Weekly Review 后，用户收到来源链接、实际转录状态和至少一项有据可查的口播分析，或清楚的失败状态。

### 14.2 调用与覆盖

- 首次使用前确认每份报告的总预算上限和每位作者每份报告的作品上限；用户同意保存后，后续报告自动复用设置，不再中途询问。
- Actor 的单次 `resultsLimit` 语义与每作者产品上限必须经多账号实测确认；只有证明确实执行了每作者上限，才能通过该验收项。
- 每个相关 Actor run 必须收到根据报告剩余预算计算的 `maxTotalChargeUsd` 或等效硬预算参数；同一份报告的所有 run 预算额度之和不得超过用户确认的报告总预算。仅在 Skill 文本中记下预算、不传入运行接口，不算通过。
- 达到每作者作品上限时按已确认规则取最近作品，并在报告中说明被上限排除的数量；这是用户首次设置的预期行为，不触发再次审批。Actor 的批次大小等技术限制若可在已确认报告预算内通过拆分 run 满足，应由 Skill 内部处理。无法在当前预算/接口能力下完成时，停止受影响的后续调用并报告部分结果，不在处理中途要求用户重新配置。
- 达到某个内部 run 的分配额度或整份报告预算上限后，报告可用结果并标为部分完成，不自动重试或启动额外 run 绕过报告总预算。
- Actor 角色与 Skill 分析分开描述；未核实的 Post Actor 字段/能力不作事实承诺。
- V1 只有账号扫描日报/周报主流程；不提供单条视频 URL 分析或跳过转录的纯帖子/指标报告。

### 14.3 内容质量和重复使用

- 日报/周报以真实 transcript 为核心，结论逐条可关联到源帖和文本证据。
- 指标只作辅助快照；缺失、错误和不完整状态准确呈现。
- 报告后提供可复制再运行请求；如宿主支持且用户授权保存设置，后续调用复用账号、报告总预算和每作者上限，不声称保存了 transcript 历史。
- 小规模试用观察首份报告是否完成、用户是否重用、转录覆盖、来源对应质量和实际用量；不预设目标数字或将用量作为唯一成功判据。

## 15. 实施和验证计划

1. **实现前接口核验：** 重新核对两个 Actor 的 live schema、账号发现到 Reel URL 的输入/输出字段、批量方式、分页、状态、权限及宿主连接。核实 Profile Posts Actor 的 `resultsLimit` 是总体还是每用户名限制，并验证每作者上限执行策略。
2. **预算参数核验：** 在选定宿主确认 Actor 调用是否支持 Apify `maxTotalChargeUsd`，并通过实际 run 或工具合同证明预算参数能传到每个 run；不支持时先调整集成方案，不以未经执行的预算值作为安全承诺。
3. **设计/离线验证：** 为时间窗、账号和 URL 匹配、预算到顶、每作者作品上限、部分结果、缺失指标和失败状态编写离线场景。
4. **真实功能验证：** 在开发完成后，再从 Codex、OpenClaw 或 ChatGPT 等宿主中选择一个最适合的环境；先确认工具、授权、预算传递和测试范围，再验证两个 Actor 的完整默认流程。一个平台通过不代表其他平台通过。
5. **用户试用：** 观察第 2 节指标与首次设置/日常复用路径；在用户知情授权范围内记录，试用结论归因于实际证据。
6. **发布门槛：** 默认转录链路、预算与每作者上限实际生效、来源关联和覆盖/失败状态均通过验证，说明用户可理解；README 只写已验证内容。公开第二个 Skill 前，按项目架构确认第一个 Skill 的独立新用户旅程复核状态，并记录证据或未完成项。

不得把未验证平台、直接 URL 输入、自动调度、持久化历史、文件导出、固定费用或固定调用量写为已支持能力。

## 16. 后续阶段

可另行评估：宿主原生或 Apify 调度器自动运行；复杂的跨会话偏好管理；历史转录检索；跨次去重和变化比较；通知；团队/多客户管理；文件导出。

这些能力需单独定义存储、授权、保留、用户控制、去重、费用和防重复运行设计，并完成验证后才能描述为可用。若宿主不能安全保存本 PRD 所需的最小运行设置，应以用户可保存的复制模板作为低摩擦替代。

## 17. 实现前待验证事项

1. `instagram-post-scraper` 的 live 输入/输出字段、账号识别、URL 类型、时间过滤、批量行为和 Dataset 完整性信号；
2. `instagram-transcripts-scraper` 处理从账号发现结果得到的 Reel URL、批量输入限制和结果对应字段；
3. 两个 Actor 分别或连续调用时的宿主工具暴露、Apify 授权、审批及用量行为；
4. `resultsLimit` 对多个用户名的作用范围及实现每作者作品上限的方式；
5. 目标宿主是否能在每个 Actor run 传递 `maxTotalChargeUsd` 或等效预算上限；
6. 每个报告可能启动多个 run 的用户可见说明，以及通过 Apify Console 查看实际用量的路径；
7. Skills 目录中的显示名称与搜索词核查，不对目录收录作承诺；
8. 各宿主的自然语言调用、Apify 连接和完整报告能力；
9. 自动时区来源及用户修改交互。
